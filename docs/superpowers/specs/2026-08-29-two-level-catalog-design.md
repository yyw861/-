# 体育商品两级分类与条码编号设计

## 1. 目标

在现有单门店体育商品进销系统中，将单层分类升级为“大类—小类”两级结构，并让条码前两位成为大类识别依据。

- 大类表示一类体育器材，例如球类、棋类。
- 小类表示一种体育器材，例如篮球、足球、围棋。
- 品牌属于具体商品，颜色、尺寸和型号等属于 SKU 规格，不进入分类层级。
- 有厂家条码时使用原条码；无厂家条码时由管理员手动输入内部条码。
- 系统不自动生成条码或分类编号。

## 2. 领域模型

商品层级固定为：

`大类 → 小类 → 品牌商品（SPU）→ 规格（SKU）→ 条码`

### 2.1 大类

大类包含：

- 两位数字编号，例如 `01`。
- 名称，例如“球类”。
- 排序值。
- 启用状态。

大类编号和名称在全系统内唯一。编号只能是两位数字，管理员手动维护。
大类编号一经其下已经存在 SKU 就不可修改；需要调整编号时，应新建正确编号的大类并按跨大类移动规则处理商品。

### 2.2 小类

小类包含：

- 所属大类。
- 独立的两位数字编号，例如 `01`。
- 名称，例如“篮球”。
- 排序值。
- 启用状态。

小类编号不与大类编号拼接。编号和名称只要求在所属大类内唯一，不同大类可重复使用相同小类编号。

### 2.3 商品与 SKU

- 商品 SPU 直接关联小类，通过小类获得所属大类。
- 商品 SPU 继续关联品牌。
- SKU 继续保存颜色、尺寸、型号等规格、零售价和库存预警值。
- 每个 SKU 保存一个厂家条码或内部条码。

不在商品上重复保存大类，避免大类与小类关系不一致。

## 3. 条码规则

厂家条码和内部条码使用同一个字段，并遵循相同规则：

- 只能包含数字。
- 长度至少为三位，不限制最大业务长度。
- 全系统唯一。
- 前两位必须等于 SKU 所属大类的两位编号。
- 无厂家条码时由管理员手动输入，系统不自动生成。
- 内部条码与厂家条码一样，可以由扫码枪或键盘用于入库、销售和库存查询。

条码前缀与大类关系由业务服务统一校验。数据库继续保证条码唯一性和基本格式；跨表的前缀一致性不依赖数据库触发器。

## 4. 数据库演进

### 4.1 目标结构

- 现有 `category` 表演进为大类表，增加两位编号。
- 新增小类表，外键关联大类，并建立“大类 + 小类编号”和“大类 + 小类名称”唯一约束。
- `product_spu` 改为关联小类；目标结构不再冗余保存大类外键。
- SKU 条码保留唯一索引，并增加数字和最小长度校验。

SQLite 迁移通过原子表重建完成。用户已确认旧业务数据不需要保留，因此升级时清空旧商品、库存、入库、销售、退货、库存调整及其流水；门店设置、单据编号配置和备份配置继续保留。

### 4.2 升级规则

1. 升级迁移在一个事务内清理旧业务记录并重建目录相关表。
2. 大类、小类、品牌、商品和 SKU 从空数据开始，由管理员按新规则重新建档。
3. 库存、进销退、库存调整、流水和对应幂等记录全部清空，避免产生无商品关联的历史记录。
4. 门店名称、联系方式、小票设置、单据前缀等系统配置不清空。
5. 迁移失败时回滚，不得留下部分升级状态。

## 5. 商品管理流程

商品管理页面按以下职责拆分：

1. 大类管理：新增、编辑、排序和启停。
2. 小类管理：先选择大类，再维护该大类下的小类编号、名称、排序和状态。
3. 商品管理：按大类和小类筛选商品，维护品牌商品及其 SKU。

编辑规则：

- 已被商品使用的大类或小类不能删除，只能停用。
- 尚无 SKU 的大类可以改号；已有 SKU 的大类编号不可修改。
- 停用大类会使其小类和商品不能参与新业务，但不改写子记录状态和历史数据。
- 商品在同一大类内移动小类时，条码无需改变。
- 商品跨大类移动时，所有 SKU 条码必须同时满足新大类前缀，否则拒绝保存。
- 被停用的大类、小类、商品或 SKU 均不能新增入库或销售。

## 6. 扫码入库流程

入库流程由“先选分类再扫码”调整为“先扫码再识别”：

1. 管理员扫描或手动输入条码。
2. 系统校验条码格式并读取前两位。
3. 系统使用前两位自动查询已启用且已确认的大类。
4. 找不到大类时阻止入库，提示先到商品管理建立对应大类。
5. 找到已有 SKU 时，系统带出大类、小类、商品和库存信息，直接进入数量、进价录入。
6. 找不到 SKU 时，系统显示识别到的大类，并要求管理员从该大类的已启用小类中选择一个。
7. 管理员填写品牌、商品名称、SKU 编码、规格、零售价和预警值，完成快速建档后录入数量和进价。

快速建档不得选择其他大类的小类。当前大类没有可用小类时，必须先到商品管理建立小类。

## 7. 销售、库存和报表

- 零售扫码继续直接按完整条码查找 SKU，并校验整个分类链条均可用。
- 库存列表、库存流水和 CSV 导出增加大类编号、大类名称、小类编号和小类名称。
- 商品、库存和历史单据查询支持大类、小类组合筛选。
- 分类销售占比默认按大类汇总。
- 用户选择某个大类后，可以下钻查看该大类下的小类销售明细。
- 低库存和商品销量排行同时展示大类与小类，金额、成本和退货计算规则不变。

新业务行继续通过 SKU 关联当前分类名称，不复制新的分类快照。本阶段不改变既有财务金额和库存成本算法。

## 8. API 边界

目录模块提供独立的大类和小类资源：

- 大类的查询、新增、修改和启停。
- 按大类查询小类，以及小类的新增、修改和启停。
- 按条码前缀查询可用大类。
- 按完整条码查询 SKU 时返回其大类和小类上下文。
- 商品创建和修改请求使用小类标识，不再由客户端分别提交可能矛盾的大类和小类。

入库、库存、报表等模块只依赖目录模块公开的分类视图和校验服务，不直接复制分类判断逻辑。

## 9. 错误处理

- 编号格式错误、条码格式错误或前缀不匹配：返回 400。
- 大类编号、分类名称、同一大类下小类编号或名称重复：返回 409。
- 条码前缀不存在：返回 404，并提供“请先建立大类”的业务提示。
- 分类链条停用：返回 409，说明需要处理的分类或商品。
- 并发修改分类或商品时沿用当前冲突处理，不允许静默覆盖。

前端保留用户输入并展示可操作的中文错误，不因失败清空入库草稿。

## 10. 测试与验收

### 10.1 自动测试

- 迁移测试：旧业务数据被清空，系统设置得到保留，新目录约束生效。
- 约束测试：大类两位编号全局唯一，小类两位编号和名称在大类内唯一。
- 服务测试：已有 SKU 的大类不能改号。
- 条码测试：数字格式、最小长度、全局唯一和前缀一致性。
- 服务测试：跨大类移动、停用分类、待确认商品均被正确限制。
- 前端测试：大类小类联动维护和错误状态保留。
- E2E：扫码识别大类、未知条码选择小类快速建档、已有条码直接入库、销售和报表下钻。
- 回归测试：库存移动平均成本、销售、退货、调整、备份和恢复不受影响。

### 10.2 验收场景

1. 建立 `01 球类`，并在其下建立 `01 篮球`、`02 足球`。
2. 扫描以 `01` 开头的未知数字条码，系统自动识别球类，只显示篮球和足球供选择。
3. 选择篮球并建立不同品牌、颜色或尺寸的商品 SKU，完成入库。
4. 再次扫描同一条码时直接找到已有商品，不再要求选择小类。
5. 扫描不存在的大类前缀时被阻止并获得明确提示。
6. 将 `01` 开头的 SKU 移到其他大类时被前缀校验阻止。
7. 销售后报表先展示球类汇总，并能下钻到篮球明细。
8. 升级旧数据库后旧业务数据已清空，门店和小票设置仍然保留，可以按新目录重新建档。

## 11. 本阶段不包含

- 第三级或任意深度分类。
- 自动生成厂家条码或内部条码。
- 根据商品名称自动判断小类。
- 一个商品同时属于多个小类。
- 供应商、采购订单、多门店或账号权限。
